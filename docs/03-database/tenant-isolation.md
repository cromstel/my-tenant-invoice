# Tenant Isolation

This document details the implementation of tenant isolation within **myTenant Invoice**, a critical security and architectural requirement. It describes the mechanisms and principles employed to ensure that each organization's data and workflows are logically and physically separated from others on a shared SaaS infrastructure.

---

## 1. Core Principle: Row-Level Isolation

**myTenant Invoice** utilizes a shared database, shared schema with **row-level multi-tenancy**. This means all tenants' data resides in the same database tables, but every tenant-specific record is explicitly linked to an `Organization` via an `organizationId` foreign key.

**Key Rule**: A user from Organization A must never be able to retrieve, infer, update, or delete information belonging to Organization B.

---

## 2. Implementation Strategy

Tenant isolation is enforced rigorously at multiple layers of the application stack:

### 2.1. Database Layer (Prisma & MySQL)

-   **`organizationId` Column**: Every table storing tenant-specific data includes a non-nullable `organizationId` column. This is the primary mechanism for data partitioning.

    ```prisma
    model Invoice {
      id             String       @id @default(cuid())
      organizationId String
      organization   Organization @relation(fields: [organizationId], references: [id])
      // ... other fields

      @@unique([organizationId, invoiceNumber]) // Ensures unique invoice numbers per org
      @@index([organizationId])
    }
    ```

-   **Prisma Query Enforcement**: All data access through Prisma ORM for tenant-scoped entities explicitly includes the `organizationId` in `where` clauses.

    ```typescript
    // WRONG: Potentially exposes other tenants' data if invoiceId is guessed
    // await prisma.invoice.findUnique({ where: { id: invoiceId } });

    // CORRECT: Enforces tenant isolation
    await prisma.invoice.findFirst({
      where: {
        id: invoiceId,
        organizationId: currentOrganizationId, // Derived from authenticated session
      },
    });
    ```

-   **Unique Constraints**: Tenant-scoped unique identifiers (e.g., `invoiceNumber`, `customerNumber`, `meterSerialNumber`) are enforced using composite unique constraints involving `organizationId`. This prevents collisions across tenants while allowing internal uniqueness.

-   **Foreign Key Relationships**: `organizationId` is a foreign key, ensuring referential integrity and preventing orphaned records.

### 2.2. API & Server Action Layer (Next.js Backend)

-   **Authenticated Context**: The `organizationId` of the currently authenticated user is **always derived from the server-side session** (e.g., from Auth.js) and is never trusted directly from client-side input.
-   **Authorization Middleware**: A global middleware or route-level guards intercept requests to tenant-scoped endpoints. These guards extract the `organizationId` from the session and inject it into the request context or pass it explicitly to services.
-   **Service/Repository Layer**: All business logic functions and data access methods receive the `organizationId` as a mandatory parameter. They are responsible for ensuring all subsequent database operations include this identifier.

    ```typescript
    // src/server/repositories/invoice.repository.ts (conceptual)
    export async function getInvoiceById(invoiceId: string, organizationId: string) {
      return prisma.invoice.findFirst({
        where: { id: invoiceId, organizationId },
        // ... other includes/selects
      });
    }
    ```

-   **Input Validation**: Zod schemas on the server-side validate all incoming data, including ensuring that any provided `organizationId` (if applicable, e.g., for platform admin actions) matches the authorized context.

### 2.3. Background Processing (BullMQ Workers)

-   **Job Payloads**: Every job added to BullMQ queues that processes tenant-specific data must include `organizationId` in its payload.
-   **Worker Enforcement**: Background job workers, upon processing a job, extract the `organizationId` from the job data and use it for all subsequent data access, identical to API layer enforcement.

### 2.4. File Storage (S3-compatible Object Storage)

-   **Storage Paths**: Files are stored in object storage (e.g., S3) with `organizationId` as part of the key/path prefix (e.g., `organizations/{organizationId}/invoices/{invoiceId}.pdf`).
-   **Signed URLs**: Access to private tenant documents is granted exclusively through time-limited, pre-signed URLs generated by the backend, which incorporate `organizationId` checks and user permissions.
-   **Bucket Policies**: Object storage bucket policies are configured to enforce granular access based on prefixes, aligning with `organizationId` partitioning.

### 2.5. Caching

-   **Cache Key Strategy**: All cached data containing tenant-specific information is keyed by `organizationId` (e.g., `org:{organizationId}:settings`, `org:{organizationId}:dashboard-metrics`).
-   **No Cross-Tenant Caching**: Platform-wide caches (if any) explicitly exclude tenant-sensitive data.

---

## 3. Security Measures and Testing

-   **Principle of Least Privilege**: System and user accounts are granted only the minimum necessary permissions.
-   **Input Sanitization**: Prevents injection attacks that could attempt to manipulate `organizationId` or bypass filters.
-   **IDOR (Insecure Direct Object Reference) Prevention**: The consistent use of `organizationId` in all data access queries inherently prevents IDOR vulnerabilities where an attacker could access another tenant's data by guessing an ID.
-   **Comprehensive Testing**: Extensive [Tenant Isolation Testing](../08-testing/tenant-isolation-testing.md) (unit, integration, E2E) is conducted to explicitly verify that cross-tenant data leakage is impossible.
    -   **Negative Test Cases**: Attempts by a user from Organization A to access data from Organization B should result in 403 Forbidden or 404 Not Found errors.
-   **Audit Logging**: All attempts at unauthorized access or suspicious activities related to `organizationId` are logged and monitored.

---

## 4. Platform-Level Data

Some data is not tenant-scoped (e.g., `User` profiles themselves, `SubscriptionPlan` definitions, global `Role` and `Permission` definitions for platform roles). Access to this data is managed by platform-level roles and does not require `organizationId` filtering, but still adheres to strict authorization checks.
