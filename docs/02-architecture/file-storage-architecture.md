# File Storage Architecture

This document outlines the file storage architecture for **myTenant Invoice**, focusing on secure, scalable, and tenant-isolated handling of user-generated and system-generated files. This includes uploads like logos, property images, and documents, as well as system outputs like PDF invoices.

---

## 1. Overview

myTenant Invoice will utilize **S3-compatible object storage** (e.g., AWS S3, MinIO for local development) for all file storage needs. This approach offers:

-   **Scalability**: Horizontally scales to accommodate vast amounts of data.
-   **Durability**: High data durability and availability.
-   **Security**: Robust access control, encryption, and secure sharing mechanisms.
-   **Cost-Effectiveness**: Tiered storage and cost-efficient scaling.
-   **Tenant Isolation**: Easy partitioning of data per tenant.

Files are not stored directly on the application servers, adhering to stateless server principles.

---

## 2. Storage Strategy

### 2.1. Object Storage Provider

-   **Production**: AWS S3 (or a cloud provider equivalent like Azure Blob Storage, Google Cloud Storage).
-   **Local Development**: [MinIO](https://min.io/) via Docker (`docker-compose.yml`) for S3-compatible local object storage.

### 2.2. Folder Structure and Tenant Isolation

Files will be stored in a tenant-isolated manner using `organizationId` as the top-level prefix within the storage bucket. This ensures logical and physical separation of tenant data.

```text
mytenant-invoice-bucket/
├── public/
│   └── marketing/
│       └── hero-image.webp
├── organizations/
│   ├── {organizationId_1}/
│   │   ├── logos/
│   │   │   └── company-logo.webp
│   │   ├── properties/
│   │   │   └── {propertyId_A}/
│   │   │       └── apartment-photo.webp
│   │   ├── documents/
│   │   │   └── {documentId_X}/contract.pdf
│   │   ├── invoices/
│   │   │   └── {invoiceId_Y}/INV-2026-00001.pdf
│   │   └── avatars/
│   │       └── {userId_Z}/profile.webp
│   └── {organizationId_2}/
│       └── ...
```

-   **Public Bucket**: A separate bucket or a dedicated `public/` prefix within the main bucket can be used for globally accessible assets (e.g., marketing images). These assets are **not** tenant-scoped.

### 2.3. File Naming Conventions

-   Descriptive filenames with a `cuid()` or UUID prefix to ensure uniqueness.
-   Example: `organizations/{orgId}/invoices/{invoiceId}/{cuid()}-INV-2026-00001.pdf`

## 3. File Operations

### 3.1. Uploads

-   **Direct Upload (Client to S3)**: For large files, consider signed URLs to allow clients to directly upload to S3, bypassing the application server. This reduces server load and improves performance.
-   **Server-Side Upload**: For smaller files or when server-side processing/validation is mandatory, files are uploaded to the application server and then proxied to S3.
-   **Validation**: All uploads undergo server-side validation:
    -   **File Type (MIME)**: Whitelist allowed MIME types (`image/webp`, `application/pdf`).
    -   **File Size**: Enforce maximum file size limits.
    -   **Malware Scanning**: Integration with a scanning service (e.g., ClamAV, AWS Rekognition for images) for critical files.
    -   **Tenant Ownership**: Associate uploaded files with the correct `organizationId`.

### 3.2. Downloads & Access

-   **Signed URLs**: For private, tenant-scoped files (e.g., invoices, private documents), access is granted via time-limited, pre-signed URLs generated by the backend. This ensures that only authorized users with valid permissions can access the files.
-   **Direct Public Access**: Public assets (e.g., marketing site images) can be accessed directly from the CDN/S3 public URL.
-   **Authorization**: All download requests for tenant-scoped files must pass through the API layer for robust authorization checks (user belongs to organization, has `document.read` permission, etc.).

---

## 4. Security Considerations

-   **Least Privilege**: S3 bucket policies and IAM roles are configured with the principle of least privilege. Application roles only have access to their designated paths.
-   **Encryption at Rest**: All files stored in S3 are encrypted at rest using AES-256 (either S3-managed keys or KMS-managed keys).
-   **Encryption in Transit**: All communication with S3 is via HTTPS/TLS 1.2+.
-   **Public Access Blocks**: S3 buckets are configured to block public access by default, only allowing explicit exceptions for truly public assets.
-   **File Deletion**: Soft deletion (`deletedAt` field in `Document` model) is preferred for critical documents, with actual object deletion handled by a background job after a retention period.
-   **MIME Sniffing Prevention**: `X-Content-Type-Options: nosniff` header is used for served files.

---

## 5. Metadata and Database Integration

The `Document` Prisma model stores metadata about each file, including:

-   `organizationId`: Critical for tenant isolation.
-   `entityType`, `entityId`: Links the document to its parent entity (e.g., `Invoice`, `Property`, `Customer`).
-   `fileName`, `fileType`, `fileSize`: Basic file information.
-   `storagePath`: The key/path in the S3 bucket (must be unique).
-   `uploadedByUserId`: Tracks who uploaded the file.

This metadata enables efficient searching, listing, and auditing of documents without directly querying object storage.

---

## 6. Image Optimization

For performance and user experience:

-   All uploaded images (e.g., property photos, logos) are automatically processed and optimized into `.webp` format.
-   Images are resized to appropriate dimensions for various display contexts.
-   `next/image` component is used for responsive image loading and lazy loading.

See also: [Image Guidelines](../06-ui-ux/image-guidelines.md)
